Principles

This methodology decomposes any complex institutional system — from central banks to regulated marketplaces to healthcare networks — into buildable specifications through a structured analytical pipeline. It is designed for agentic development teams consuming machine-readable artefacts, managed by a human programme owner.

Core tenets

  1. Capabilities first, technology second. Start from what the organisation does, not what systems it needs. Capabilities are business domain groupings containing services, not single services. Technology choices are derived from capability requirements, never the reverse.
  2. Journeys are the unit of delivery. Every data model, API contract, and event specification traces back to a persona journey. Nothing exists in the system that isn't required by at least one journey. Journeys are design-time specifications, not runtime orchestration.
  3. Artefacts are machine-readable. Every output is a validated JSON document stored in version control. No PDFs, no slide decks, no documents that can't be consumed by an agentic development team.
  4. Sequential discovery, iterative modelling. The first six steps are done once in order. Steps 7-13 are repeated per journey, with feedback loops between them.
  5. Cross-capability communication is exclusively async events. Services within a capability communicate freely. Capabilities never call each other's APIs. The Event Bus is the sole cross-capability integration mechanism.
  6. Three architectural layers. The Capability Layer (runtime business domain groupings), the Platform Layer (runtime shared infrastructure), and the Contract Layer (design-time specifications). C4 diagrams show runtime only.
  7. Transparency is a capability, not a feature. If the organisation has public accountability obligations, transparency is modelled as a first-class capability with its own services, projections, and disclosure timelines.
Design vs development. This methodology produces a headless system specification, not running software. The output is consumed by a separate development pipeline (your DEV project) which builds, tests, and deploys the actual system. Channel UIs (web, mobile, branch, partner portals) sit outside the system boundary and are a separate development concern consuming the capability APIs produced here. The handoff point is a stable journey model in Phase C — each stable journey constitutes one buildable vertical slice.

Architecture specification

The architecture is capability-driven: the system is decomposed into distinct business capabilities that own their data, publish event contracts, and expose REST APIs. The architecture has two runtime layers and one design-time layer.

What a capability is

A capability is a business domain grouping. It represents what the organisation does, not how the software is built. A capability is not a single deployable service. It is a grouping of one or more independently deployable technical services that together fulfil a business domain's responsibilities.

Each capability contains:

  • One or more technical services — APIs, workers, processors, scheduled jobs, or any other deployment unit the domain requires
  • Its own data — one or more databases or database schemas. Services within a capability may share a database or have their own. This is an internal decision, invisible to other capabilities.
  • Published event contracts — the events it produces, registered in the Schema Registry
  • Consumed event subscriptions — the events it listens for from other capabilities
  • A REST API surface — exposed to external consumers (channel UIs, internal tooling, external partners)

Communication rules

Within a capability (free)

Services within a capability communicate by whatever means makes sense for the domain: synchronous REST/gRPC, shared database access, direct method calls, or internal message queues. The architecture does not prescribe internal communication. The capability boundary is a business domain boundary, not a technical communication boundary.

Across capabilities (events only)

Communication between capabilities is exclusively asynchronous events through the Platform Layer's Event Bus. A capability never calls another capability's API directly. A capability never reads from or writes to another capability's database. A capability never communicates synchronously with another capability.

Channel interaction (external REST)

Channel UIs (customer-facing apps, websites, internal tooling, partner portals) sit outside the system boundary. They interact with capabilities through their published REST APIs using standard stateless request-response calls. A channel may call multiple capabilities in sequence to assemble a user journey. The channel orchestrates the user interaction; the event bus orchestrates the cross-capability consequences.

Three architectural layers

Capability LayerRuntimeBusiness domain groupings containing independently deployable technical services. Each capability owns its data, publishes events, and exposes REST APIs.

There are exactly four ways a service can be reached. No other communication paths exist. Services are never directly addressable from outside their capability.

A persona (credit analyst, customer, officer) always interacts through a channel; the channel calls the capability. Channel services and platform services are excluded from cross-capability violation checks.

Journey state

User journeys are not orchestrated by a central process manager or saga. Journey state is implicit in the data held by capabilities. There is no separate state machine. The data IS the state. Coordination happens through capabilities reacting to each other's published events.

Key architectural principles

  1. Capabilities are business domain groupings, not deployment units. A capability contains one or more independently deployable services.
  2. Cross-capability communication is exclusively asynchronous events. No synchronous calls between capabilities.
  3. Share the mechanism, isolate the state. Platform infrastructure is shared; business data is isolated per capability.
  4. Each capability owns its own data representations. No shared data models. Synchronisation through domain events.
  5. Journey state is implicit in capability data. No central orchestrator or saga.
  6. The Contract Layer is design-time, not runtime. The Schema Registry is the sole runtime manifestation.
  7. C4 diagrams show only what runs in production.
  8. Capabilities are sized to fit within an AI agent's context window. This is the primary decomposition constraint.

Phase model

Phase A — Discovery (sequential, do once)

Produces the stable foundation: what the organisation does, what constrains it, and who interacts with it. Each step depends on the completed output of the previous step. Outputs are baselined and rarely revised.

Phase B — Framing (sequential, do once)

Produces the system map and the prioritised journey backlog. These are the inputs that enable all subsequent iterative work. The visual architecture becomes a living document enriched by later phases.

Phase C — Analytical modelling (iterative, per journey)

Pick the next highest-priority journey. Work through steps 7-13 for that journey. Aggregate outputs into the central data model, service map, and event catalogue. Update the C4 workspace. Repeat. A journey may span multiple capabilities — the sequence diagram makes cross-capability data flows visible. Steps within a journey form a tight feedback loop — discovering a missing entity in step 12 sends you back to step 10. Each stable journey is immediately available for handoff to DEV.

Headless system specification. This pipeline produces a headless system specification. Channel UIs (web, mobile, branch, partner portals) sit outside the system boundary and are a separate development concern. They consume the capability APIs and journey contracts produced here. Channel teams start once the first journey's API contracts are stable.

Deterministic vs reasoning split

The pipeline divides work into scripted (deterministic) operations and reasoning (agent) operations. Neither replaces the other — they handle fundamentally different concerns.

Sequential vs iterative: understanding the two rhythms

The 13 steps are not a waterfall. They cluster into two fundamentally different working rhythms, and confusing the two is the most common way to misapply this methodology.

Phases A and B are convergent and sequential

You are narrowing from the universe of possibilities down to a fixed set of capabilities, personas, and a prioritised journey backlog. Each step depends on the completed, reviewed, and baselined output of the previous step. You cannot identify personas (step 4) until you know what capabilities exist (step 1). You cannot inventory journeys (step 6) until you know who the personas are (step 4) and what the architecture looks like (step 5). The total number of steps here is small (6), they flow in strict order, and the outputs are stable — you don't revisit "what are the capabilities" once you've moved on.

The working rhythm is: produce an artefact, review it, baseline it, move to the next step. The Jira workflow reflects this — FOUND uses a Kanban board where artefacts move through Draft → In review → Approved → Baselined, with review gates between steps.

Phase C is divergent and iterative

You are expanding outward from each journey into increasing specificity, and every journey you model teaches you something that changes the central model. The second journey you model will discover that the Institution entity from the first journey needs three new fields. The third journey will reveal that what you thought was one service is actually two. The fifth journey will expose a service boundary that was drawn in the wrong place. This is expected and healthy — the iteration is the methodology, not a failure of it.

Phase C iterates per journey — you pick a journey, work through steps 7-13, aggregate the results into the central model, and pick the next journey. Each stable journey is immediately available for handoff to DEV as a buildable vertical slice.

Gate points between phases

Two explicit gate points control the flow:

GateBetweenCondition to pass
Gate 1: Modelling readinessPhase B → Phase CAll foundation artefacts are baselined (including C4, service dependencies, observability model, security model). The journey inventory is prioritised. The first journey is selected.

Gate 1 is passed once and never revisited. Gate 2 is passed repeatedly — each time a journey reaches "stable", it is immediately available for handoff to DEV as a buildable vertical slice.

What this means for scheduling

Phases A and B take 2-3 weeks with the domain analyst and architect working as a pair. Sprint 0 (platform + environments) takes 1-2 weeks and overlaps with the start of Phase C. Phase C then runs for 8-12 weeks, modelling journeys in priority order. The total design pipeline is 10-14 weeks, but the DEV team receives Sprint 0 at week 3 and buildable journey units from week 5 onwards — they don't wait for all design to complete.

The pipeline, not the waterfall. The overall flow is: Phase A → Phase B → [Sprint 0 to DEV + Phase C feeding DEV incrementally per journey]. Design and development overlap. The first journey can be in production while the fifteenth journey is still being modelled. Channel development (web, mobile, branch, partner portals) runs as a separate concern, consuming the capability APIs and journey contracts produced here. Channel teams start once the first journey's API contracts are stable.

Step 1 — Capabilities

PHASE A · STEP 1
Identify organisational capabilities

Define what the organisation does at the highest level of abstraction. Each capability is a business domain grouping containing one or more independently deployable technical services. Capabilities are stable over decades — they change only when the organisation's mandate changes.

Before drafting any capability artefact, the agent must research the market context for the organisation's sector. A capability list derived only from the org chart or mandate produces a shallow architecture. The research captures:

  • Competitive landscape — who does what, what's being unbundled/re-bundled, where is the margin, who are the top incumbents and challengers
  • Regulatory horizon — what's coming in 2-3 years that will create new capabilities or reshape existing ones, what enforcement actions signal regulator focus
  • Build-vs-buy assessment — what platforms exist (BaaS, SaaS), what must be built in-house for regulatory or competitive reasons
  • Sub-capability boundary evidence — market structure informs the promotion test (specialist providers = distinct participants, separate regulation = separate framework, distinct product = distinct lifecycle)
Inputs
Organisational mandate, legislation, charter, strategic plan, annual reports, market research
Outputs
capabilities/*.json — one file per capability with name, description, legislative basis, market context, and structured sub-capabilities. Also contributes to foundation/shared-sub-capabilities.json when overlaps are detected.
Owner
Domain analyst leads. Agent researches market landscape and generates first draft. Human validates against institutional reality and applies promotion tests.

Sub-capability promotion test

Every sub-capability must be evaluated against four criteria. If it meets three or more, it should be promoted to a separate service within the capability. Promotion does NOT mean leaving the capability — a promoted sub-capability is still part of its parent capability. It becomes its own service (own repo, own deployment unit) but remains inside the capability boundary. Promoted services may share databases with other services in the same capability or have their own — this is an internal decision.

CriterionQuestionExample (syndicated lending)
Distinct external participantsDoes it involve participant types absent from the parent?Yes — agent banks, participant banks
Distinct legal/regulatory frameworkIs it governed by its own legislation or industry standard?Yes — LMA documentation
Distinct lifecycleDoes it have end-to-end phases that don't map onto the parent?Yes — bookbuilding, allocation, agency administration
Independent scalability requirementsDoes it have different demand drivers from the parent?Yes — syndication volumes independent of bilateral lending
Retained vs promoted: Retained sub-capabilities are implemented as internal modules within an existing service (shared database, direct method calls). Promoted sub-capabilities become their own service but remain inside the capability boundary. Cross-capability communication rules do not apply within the capability boundary.
Promotion result values: promote_to_service (3-4 criteria met — becomes a separate service within the capability), remain_sub_capability (0-2 criteria met — stays as an internal module), review_in_phase_c (borderline — 2 criteria met but complexity is uncertain, defer decision until journey modelling).

Service dependencies (T0-T4 tier framework)

Every service is assigned a build tier based on its upstream dependencies. Each dependency is classified by criticality (hard = sync, immediate failure if down; soft = async/degradable). The build order is regulatory-driven: compliance prerequisites must be live before payment or onboarding services.

Data integrity validation

The validate-data-integrity.py script performs a deep field-level traceability check across all artefacts for a journey. It is run by the Review Team at Stage 1, after validate-sequences.py passes. It is the most thorough deterministic check in the pipeline — it catches approximately 80% of issues that would block a developer before the handoff reaches the DEV team.

The traceability chain

The validator traces a single path through the artefact stack:

Entity fields (data-model.json)
  → Event payload fields (event-catalogue / events/*.json)
    → Consumed event mappings (service-boundaries.json consumed_events)
      → API contract request/response fields (api-contracts/*.openapi.json)

Any break in this chain — a field referenced in an event payload that doesn't exist in its source entity, an API response field that has no entity backing, a consumed event mapping that refers to a field not present in the event schema — is surfaced as a validation failure.

Eight checks performed

#CheckWhat it catches
1Entity field coverageEvery field referenced in event payloads resolves to a field in its owning entity's data-model.json
2Event payload completenessEvery event in events/*.json has a non-empty schema with typed fields
3Consumed event mapping resolutionEvery maps_to entry in consumed_events references a field that exists in the consuming service's entities
4API response entity backingEvery response field in the OpenAPI spec traces to a field in an entity owned by the responding capability
5API request field validationEvery request body field that is stored (not just passed through) has a corresponding entity field to receive it
6Cross-step lineage continuityFields declared in cross_step_lineage[] in the step manifest exist in both the producing and consuming steps
7Derived field declarationsFields marked computed_from in the data model have all their source fields present in the same entity or declared cross-entity
8Outbound event derivation coverageEvents with a derived_from section reference only fields present in the publishing service's owned entities
Run order matters. validate-data-integrity.py must run after validate-journey.py and validate-sequences.py. It assumes file structure and ID formats are already clean. Running it on an artefact set with ID format errors will produce misleading results.

Process improvements

Generalised learnings from running the full pipeline across 30 journeys. These inform script design, team instructions, and review gates. They are recorded here so teams starting a new project can apply them from journey 1 rather than rediscovering them.

Early journeys set the quality bar

The first 5 journeys modelled before scripts and standards existed required full remediation afterwards — ID format renames, cross-capability violation fixes, central model sync. Later journeys modelled with the scaffold + manifest + validate loop passed first time or with minor fixes. Invest in tooling and standards before the first journey. The scaffold script, manifest format rules, and validation scripts pay back their setup cost by journey 3.

Central model entity sync is the #1 failure mode

Across 30 journeys, the agent forgot to create central-model/entities/ files in approximately 30% of runs. It consistently updated service-map.json and event-catalogue.json but omitted the individual entity files. The sync-central-model.py script eliminates this entirely — it creates missing entity files automatically from the journey's data-model.json. Never rely on the agent for deterministic file operations.

Annotated IDs persist despite explicit instructions

The agent writes "ENT-012 (MortgageApplication)" in owned_entities and published_events in approximately 20% of runs despite the manifest specifying plain IDs only. The cleanup-ids.py script runs after every journey. Accept this as a known agent behaviour pattern and script around it — do not add further instructions to the manifest expecting the problem to disappear.

Sequence diagram JSON and Mermaid diverge

The agent sometimes produces only the Mermaid .mmd without the JSON, or vice versa. In some cases the JSON steps array was present but empty (stub file). The validator catches both conditions. Both files must exist and both must have content. The JSON is the source of truth; the Mermaid is the renderable representation — they must be committed together.

Programme Lead cannot persist across many journeys

The orchestrating agent hits context or rate limits after 2–3 journeys. Design for re-spawn: the Programme Lead reads pipeline state from PIPELINE-STATE.md and the artefact directory (which journeys have models, which are stable) rather than maintaining in-memory state. This is not a failure condition — it is the expected operating model. All state lives on disk.

API contracts must be per-capability, not per-service

Early journeys produced one OpenAPI spec per service (e.g. retail-banking-core.openapi.json, customer-onboarding.openapi.json, kyc-aml.openapi.json). Later journeys correctly produced one per capability (e.g. retail-banking.openapi.json, commercial-banking.openapi.json). The per-service approach leaks implementation detail and contradicts the architecture — channels call capabilities, not services. The first journey that touches a capability creates its contract; subsequent journeys extend it.

Cross-capability violations appear in JSON, not Mermaid

Synchronous cross-capability calls tend to appear in the JSON sequence files rather than in the Mermaid files. The visual Mermaid notation makes violations obvious — the boundary is drawn explicitly. The JSON files use raw service IDs where the capability boundary is not visible. Both files are validated by validate-sequences.py, but pay closer attention to the JSON files during reasoning review. When a journey produces its sequence diagrams, check the JSON steps array explicitly for synchronous calls between services in different capabilities.

Data transformation gaps appear late and block developers

The pipeline produces data at rest (data model), call order (sequence diagrams), and payload schemas (event catalogue) — but does not natively capture how data transforms as it flows. Four transformation types are commonly missing: inbound event mapping (how a consumed payload maps to internal entities), outbound event derivation (which entity fields populate which payload fields), API response projection (field-level projection per persona/entitlement), and cross-entity derivation (computed fields spanning multiple entities). These are L3 concerns — add them as extensions to existing artefacts rather than new artefact types. The step manifest and data integrity validator surface the gaps before handoff.

Canonical schema standardisation eliminates structural drift

Across a multi-project run, artefacts produced in months 1–3 had different structures from artefacts produced in months 6–8 — field renames, optional fields that later became required, inconsistent nesting. This made cross-journey queries and automated processing unreliable. Establishing the seven canonical schemas (journey-detail, participant-interaction, data-model, service-boundaries, event-catalogue, nfr, step-manifest) as required standards, enforced by validate-journey.py at review time, eliminates structural drift. Use migrate-to-canonical-schema.py once to bring legacy artefacts into conformance. Every new journey should validate against the schemas from journey 1 — do not defer schema enforcement until the migration problem is unavoidable.

They are separate concerns staffed by different teams with different workflows.

The handoff contract

A journey is "ready for development" when all of the following are true:

  • All MODEL spec tasks for that journey are in "stable" status
  • The central model has been updated to include the journey's entities, services, and events
  • The C4 workspace has been updated
  • No blocking refinements outstanding

The dev team should never build from artefacts that are still in "in progress" or "in review" — the risk of rework is too high. The "stable" status exists precisely to signal buildability.
