## Stack

- **AWS provider** -- primary cloud (adaptable to GCP/Azure)
- **State backend:** S3 bucket + DynamoDB table for locking
- **Linting:** tflint (Terraform linter with AWS ruleset)
- **Security scanning:** checkov (static analysis for misconfigurations)

## Conventions

### General
- All infrastructure is defined in Terraform HCL -- no ClickOps, no manual changes
- Never hardcode values -- use variables with sensible defaults
- Never commit secrets or credentials to `.tf` files -- use Secrets Manager references
- Never commit `.terraform/` directories or state files
- Pin provider versions and module versions explicitly

### Naming convention
- All resources follow: `{project}-{env}-{resource}` (e.g., `treemail-prod-api-ecs`)
- Use lowercase and hyphens, never underscores or camelCase in resource names
- Terraform resource names (the label in HCL) use underscores: `resource "aws_ecs_service" "api_service"`
- Variable names use underscores: `var.database_instance_class`

### Module design
- One module per infrastructure concern (VPC, RDS, ECS, etc.)
- Modules expose only what consumers need via `outputs.tf`
- Modules accept environment-specific values via `variables.tf` with descriptions
- Modules must not assume a specific environment -- parameterise everything
- Every module has a `README.md` auto-generated by `terraform-docs`
- Modules must not contain provider blocks -- providers are defined in root modules only

### Environment parity
- All environments use the same modules -- only variable values differ
- `terraform.tfvars` per environment controls instance sizes, replica counts, etc.
- Dev: minimal resources (single-AZ, small instances, no multi-AZ)
- Staging: mirrors prod topology at smaller scale
- Prod: full redundancy (multi-AZ, autoscaling, enhanced monitoring)

### Remote state
- State stored in S3 with versioning enabled
- DynamoDB table for state locking (prevents concurrent applies)
- One state file per environment (`environments/{env}/`)
- Shared resources have their own state (`shared/state-backend/`, `shared/ecr/`)
- State bucket bootstrapped manually once via `shared/state-backend/main.tf`

### Tagging policy
- Every resource must have these tags (enforced by tflint rules):
  - `Project` -- project name (e.g., `treemail`)
  - `Environment` -- `dev`, `staging`, `prod`
  - `ManagedBy` -- `terraform`
  - `Owner` -- team or individual responsible
  - `CostCenter` -- billing allocation code
- Use `default_tags` in the provider block for common tags
- Module-specific tags are merged with defaults

### Security
- **Encryption at rest** enforced on all storage (RDS, ElastiCache, S3, EBS)
- **Encryption in transit** enforced (TLS 1.2+ on all endpoints)
- **Least-privilege IAM** -- no `*` in action or resource unless absolutely necessary
- **No public subnets for data stores** -- RDS, ElastiCache in private subnets only
- **Security groups** -- default deny, explicit allow per service
- **VPC flow logs** enabled on all VPCs
- **S3 bucket policies** -- block public access on all buckets
- **Secrets in Secrets Manager** -- never in SSM Parameter Store plaintext
- checkov runs on every PR to catch misconfigurations before apply

### State management
- Never modify state manually (`terraform state mv/rm`) without team review
- Use `terraform import` to bring existing resources under management
- Document any state surgery in PR description
- Always `terraform plan` before `terraform apply` -- never apply blindly

### Testing
- `terraform validate` on every module (syntax and type checks)
- `tflint` on every module (AWS best practices, naming, tagging)
- `checkov` on every module (security misconfigurations, compliance)
- `terraform plan` on every PR (reviewers inspect the plan diff)
- Optional: terratest for integration testing of module outputs

## Common commands (planned)

```bash
# Initialise (per environment)
cd environments/dev && terraform init

# Plan changes
terraform plan -out=plan.tfplan

# Apply changes (after review)
terraform apply plan.tfplan

# Format all files
terraform fmt -recursive

# Validate syntax
terraform validate

# Lint
tflint --recursive

# Security scan
checkov -d .

# Auto-generate module docs
terraform-docs markdown table modules/vpc/ > modules/vpc/README.md

# Import existing resource
terraform import aws_s3_bucket.example my-bucket-name

# Show current state
terraform state list
terraform state show aws_ecs_service.api_service
```

## CI/CD approach

- **Plan on PR:** GitHub Actions runs `terraform fmt -check`, `tflint`,
  `checkov`, and `terraform plan` on every PR. Plan output is posted as a
  PR comment for review.
- **Apply on merge:** merge to main triggers `terraform apply` for the
  changed environment. Requires PR approval.
- **Manual apply for prod:** production applies require explicit workflow
  dispatch approval (not auto-triggered on merge).
- **State locking:** DynamoDB lock prevents concurrent applies.
- **Drift detection:** scheduled workflow runs `terraform plan` nightly and
  alerts if drift is detected (plan is non-empty).
