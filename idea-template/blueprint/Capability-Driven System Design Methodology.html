Principles

This methodology decomposes any complex institutional system — from central banks to regulated marketplaces to healthcare networks — into buildable specifications through a structured analytical pipeline. It is designed for agentic development teams consuming machine-readable artefacts, managed by a human programme owner.

Core tenets

  1. Capabilities first, technology second. Start from what the organisation does, not what systems it needs. Technology choices are derived from capability requirements, never the reverse.
  2. Journeys are the unit of delivery. Every data model, API contract, and screen specification traces back to a persona journey. Nothing exists in the system that isn't required by at least one journey.
  3. Artefacts are machine-readable. Every output is a validated JSON document stored in version control. No PDFs, no slide decks, no documents that can't be consumed by an agentic development team.
  4. Sequential discovery, iterative modelling. The first six steps are done once in order. Steps 7–19 are repeated per journey and per portal, with feedback loops between them.
  5. Transparency is a capability, not a feature. If the organisation has public accountability obligations, transparency is modelled as a first-class capability with its own services, projections, and disclosure timelines.
Design vs development. This methodology produces specifications, not running software. The output is consumed by a separate development pipeline (your DEV project) which builds, tests, and deploys the actual system. The handoff point is a stable journey model in Phase C plus approved screen specs in Phase D — together they constitute a buildable unit of work.

Phase model

Phase A — Discovery (sequential, do once)

Produces the stable foundation: what the organisation does, what constrains it, and who interacts with it. Each step depends on the completed output of the previous step. Outputs are baselined and rarely revised.

Phase B — Framing (sequential, do once)

Produces the system map and the prioritised journey backlog. These are the inputs that enable all subsequent iterative work. The visual architecture becomes a living document enriched by later phases.

Phase C — Analytical modelling (iterative, per journey)

Pick the next highest-priority journey. Work through steps 7–13 for that journey. Aggregate outputs into the central data model and service map. Repeat. Steps within a journey form a tight feedback loop — discovering a missing entity in step 12 sends you back to step 10.

Phase D — UI specification (iterative, per portal)

Take all journeys that flow through a portal and design its screens holistically. Steps 14–19 produce the specifications that let an agentic dev team build working UIs. Gaps discovered here feed back into Phase C as refinement tickets.

Phases C and D run in parallel. Phase D can begin as soon as the first batch of Phase C journey models reach "stable" status. The design team continues modelling new journeys in Phase C while UI specifications are being written for completed journeys in Phase D. Managing the flow between these phases is the programme owner's primary job.

Step 1 — Capabilities

PHASE A · STEP 1
Identify organisational capabilities

Define what the organisation does at the highest level of abstraction. Each capability is a distinct area of institutional responsibility that could, in principle, be delegated to a separate department. Capabilities are stable over decades — they change only when the organisation's mandate changes.

Inputs
Organisational mandate, legislation, charter, strategic plan, annual reports
Outputs
capabilities/*.json — one file per capability with name, description, legislative basis, and structured sub-capabilities. Also contributes to foundation/shared-sub-capabilities.json when overlaps are detected.
Owner
Domain analyst leads. Agent generates first draft from public sources. Human validates against institutional reality and applies promotion tests.

Sub-capability promotion test

Every sub-capability must be evaluated against four criteria. If it meets three or more, it should be promoted to a standalone capability. The test is documented in the artefact so the decision can be revisited in Phase C if journey modelling reveals more complexity than expected.

CriterionQuestionExample (syndicated lending)
Distinct external participantsDoes it involve participant types absent from the parent?Yes — agent banks, participant banks
Distinct legal/regulatory frameworkIs it governed by its own legislation or industry standard?Yes — LMA documentation
Distinct lifecycleDoes it have end-to-end phases that don't map onto the parent?Yes — bookbuilding, allocation, agency administration
Distinct data domainDoes it require entities not shared with sibling sub-capabilities?Yes — syndicate_member, participation_agreement, agency_fee_schedule
Promotion result values: promote_to_capability (3–4 criteria met — extract to its own capability file), remain_sub_capability (0–2 criteria met — stays where it is), review_in_phase_c (borderline — 2 criteria met but complexity is uncertain, defer decision until journey modelling).

Shared sub-capability registry

When a sub-capability appears in more than one capability, it gets an entry in foundation/shared-sub-capabilities.json. This file records the overlap and the architectural resolution — how the shared concern will be handled at the service level.

{
  "shared_sub_capabilities": [
    {
      "id": "sanctions_screening",
      "claimed_by": [
        {
          "capability": "client-onboarding",
          "context": "Point-in-time screening during onboarding",
          "lifecycle_phase": "initial_assessment"
        },
        {
          "capability": "compliance-and-financial-crime",
          "context": "Ongoing periodic and event-triggered screening",
          "lifecycle_phase": "continuous_monitoring"
        }
      ],
      "resolution": "single_service_multiple_consumers",
      "notes": "One screening service with two consumption patterns. Onboarding calls it synchronously during application. Compliance calls it on a schedule and on trigger events. Same underlying sanctions list, different invocation patterns."
    }
  ]
}

Resolution patterns

PatternWhen to useExample
single_service_multiple_consumersSame logic, different invocation patternsSanctions screening: same list, called at onboarding vs ongoing
shared_data_separate_logicSame underlying data, different business rules appliedCollateral valuation data shared, but ELA and reserves apply different haircut frameworks
duplicate_by_designIntentionally separate despite surface similarityInternal audit vs external regulatory reporting: different authority chains and disclosure rules

Definition of done

  • Every area of organisational responsibility is represented
  • No capability overlaps with another (clear boundaries)
  • Each capability has a legislative or charter basis
  • Promotion test applied to every sub-capability — results documented in each sub-capability object
  • Any sub-capability meeting 3+ promotion criteria has been extracted to its own capability file
  • All overlapping sub-capabilities recorded in shared-sub-capabilities.json with a resolution pattern
  • Every sub-capability has a description and at least one primary persona
  • Reviewed and approved by domain analyst

Step 2 — Technical services

PHASE A · STEP 2
Map supporting technical services and cross-cutting services

For each capability, identify the technical services required to support it. Then identify services that appear across multiple capabilities — these are the cross-cutting shared services that form the integration backbone. Finally, identify the foundation infrastructure layer beneath everything.

Inputs
Capability definitions from step 1, including shared sub-capability registry
Outputs
technical-services/*.json — one file per service with capability mappings and cross-cutting flag
Owner
Agent + Architect — agent enumerates services from capabilities, architect validates technical feasibility and identifies shared services
Shared sub-capability cross-reference. For each entry in shared-sub-capabilities.json, validate that the declared resolution pattern is reflected in the technical service mapping. If the resolution is single_service_multiple_consumers, there must be exactly one technical service listed for that concern, consumed by multiple capabilities. If the resolution is shared_data_separate_logic, there should be one data service and separate logic services per capability. If the resolution is duplicate_by_design, there should be separate technical services with no shared dependency. Mismatches between the sub-capability resolution and the service mapping are a design error — resolve before proceeding to step 3.

Service classification

LayerDescriptionExample
Domain-specificUnique to one capabilityMarket ops trading system (monetary policy only)
Cross-cuttingShared across 2+ capabilitiesCounterparty management (4 capabilities)
FoundationInfrastructure beneath all servicesIAM, audit logging, PKI, networking

Artefact schema

{
  "id": "counterparty-management",
  "name": "Counterparty management system",
  "layer": "cross_cutting",
  "capabilities_served": [
    "monetary-policy",
    "lender-of-last-resort",
    "fx-reserves",
    "government-banker"
  ],
  "description": "Golden source for all counterparty identity...",
  "integration_patterns": ["synchronous_api", "event_publish"]
}

Step 3 — Governance mapping

PHASE A · STEP 3
Map governance and policy rules per capability

Capture the legislative, regulatory, and internal policy constraints that bound each capability. These rules shape who can do what (constraining personas and journeys) and what conditions must be met (constraining data models and workflows). Without this step, you risk designing journeys that don't reflect real-world approval chains and regulatory obligations.

Inputs
Capability definitions, legislation, regulatory frameworks, internal policy documents, delegated authority matrices
Outputs
governance/*.json — rules per capability with authority levels, approval chains, constraints, and disclosure obligations
Owner
Domain analyst leads — this requires deep institutional knowledge. Agent assists with structuring but cannot validate correctness.

Artefact schema

{
  "id": "ela-authority-limits",
  "capability": "lender-of-last-resort",
  "rule_type": "delegated_authority",
  "description": "ELA facilities above £1bn require governor approval",
  "authority_levels": [
    { "threshold": "up_to_500m", "approver": "director_financial_stability" },
    { "threshold": "500m_to_1bn", "approver": "deputy_governor" },
    { "threshold": "above_1bn", "approver": "governor" }
  ],
  "disclosure_obligation": {
    "oversight_body": "treasury_select_committee",
    "timing": "within_48_hours",
    "classification": "confidential_until_facility_closure"
  },
  "legislative_basis": "Central Bank Act 2020, Section 23(4)"
}

PHASE A · STEP 4

Identify every person or organisational role that interacts with the capabilities. Group them by internal (employees of the organisation) and external (counterparties, regulators, the public). Each persona maps to specific capabilities and will drive the journey inventory in step 6.

Inputs
Capabilities, governance rules, organisational charts, stakeholder analysis
Outputs
personas/*.json — one file per persona with capability touchpoints and access classification
Owner
Agent + Domain analyst — agent generates from capabilities, domain analyst validates completeness and adds tacit knowledge about real roles

Step 5 — Visual architecture

PHASE B · STEP 5
Produce the system architecture map

Synthesise capabilities, technical services, and personas into a layered architecture diagram. This is the single visual that communicates the entire system to stakeholders. It includes three layers (capability domains, cross-cutting services, foundation infrastructure) plus a channel model showing how different participant types access the system.

Inputs
All Phase A outputs
Outputs
architecture/visual-architecture.json and architecture/channel-model.json
Owner
Architect + Agent — architect defines the layering, agent produces the structured representation, both iterate on the visual

Channel model

The channel model defines how each participant type accesses the system. Each channel has its own authentication model, rate limits, data projection rules, and audit requirements.

ChannelParticipantsAuth modelProjection

External institution portalCommercial banks, regulated entitiesInstitutional credentialsConstrained per-institution

Public transparency portalPublic, oversight bodiesAnonymousTransparency projections with delay rules
M2M API channelInstitutions (direct integration)mTLS + API keysSame as external portal

Step 6 — Journey inventory

PHASE B · STEP 6
Inventory and prioritise all persona journeys

For every persona, enumerate the journeys they take through the capabilities. Each journey is a sequence of interactions that achieves a goal. Prioritise journeys by: how many capabilities they cross (complex journeys surface more shared entities), how many personas they involve (multi-participant journeys test the projection model), and institutional criticality. Journeys now trace to sub-capabilities (by ID) in addition to capabilities, tightening the link between "what the organisation does" and "what journeys users take."

Inputs
Personas, capabilities (with structured sub-capabilities), governance rules, shared sub-capability registry
Outputs
journeys/inventory.json — prioritised list with metadata per journey including sub-capability traceability
Owner
Agent + Domain analyst — agent generates comprehensive list from sub-capability × persona matrix, domain analyst prioritises and validates

Artefact schema

{

    {
      "id": "ela-facility-approval",
      "name": "Assess and approve an emergency liquidity facility",
      "personas": ["emergency-lending-officer", "commercial-bank-treasurer"],
      "capabilities": ["lender-of-last-resort", "financial-oversight", "payment-systems"],
      "sub_capabilities": [
        "lender-of-last-resort.emergency_lending_assessment",
        "lender-of-last-resort.collateral_acceptance",
        "financial-oversight.supervisory_profile_review",
        "payment-systems.rtgs_settlement"
      ],
      "shared_sub_capabilities_touched": ["collateral_valuation"],
      "priority": 1,

      "cross_boundary": true,
      "estimated_entities": 14,

Sub-capability traceability. The sub_capabilities field uses dot notation (capability.sub_capability) to maintain the parent relationship. The shared_sub_capabilities_touched field references entries in shared-sub-capabilities.json — when modelling this journey in Phase C, the modeller must check the shared registry and ensure the data model and service boundaries are consistent with the declared resolution pattern for each shared sub-capability.

Step 8 — Participant interaction model

PHASE C · STEP 8
Define projections, entitlements, and notifications per participant

For each journey phase, define what each participant type sees (data projection), what they can do (action entitlement), how they're notified (notification routing), and when information becomes visible (temporal visibility). This is where the internal/external boundary is made explicit.

Inputs
Journey detail, governance rules, channel model
Outputs
models/{journey}/participant-interaction.json
Owner
Domain analyst + Architect — domain analyst defines what each participant should see, architect validates technical feasibility of the projection model

Four concerns per phase

ConcernQuestionExample
Data projectionWhat fields does this participant see?Institution sees request status; officer sees status + supervisory profile
Action entitlementWhat can this participant do?Institution can submit collateral; officer can create assessment
Notification routingHow are they told about changes?Institution: portal notification; governor: dashboard summary
Temporal visibilityWhen does information become visible?Approval exists internally before institution is notified
Transparency projection. If transparency is a capability, add a "public" column to the participant interaction model for every journey. Define what the public sees, when they see it, and at what granularity. Use transparency tiers: immediate delayed 30d delayed 1y aggregate only permanent restrict

Step 9 — Non-functional requirements

PHASE C · STEP 9
Capture performance, consistency, and security constraints

For each journey phase, define the non-functional requirements that constrain the data model and service architecture. The difference between "this can take 24 hours" and "this must complete in 90 seconds during a market crisis" fundamentally changes the design.

Inputs
Journey detail, governance rules, institutional SLAs
Outputs
models/{journey}/nfr.json
Owner
Architect + Domain analyst — architect proposes constraints, domain analyst validates against operational reality

NFR categories

CategoryExample for ELA intake phase
LatencyRequest acknowledgement within 30 seconds; full assessment within 4 hours for urgent tier
ConsistencyStrong consistency for facility state transitions; eventual consistency acceptable for audit events
Availability99.99% — ELA is a crisis capability, must work when everything else is failing
Data classificationRESTRICTED — highest sensitivity level in the central bank
Audit depthEvery action logged with actor, timestamp, source IP, and classification
ThroughputLow volume (handful of facilities per decade) but zero tolerance for failure

Aggregation rule

After completing the data model for a journey, merge new and updated entities into central-model/entities/. If an entity already exists (e.g. Institution from a previous journey), compare fields and add any new ones discovered. If fields conflict, resolve with the architect and record the decision.

Step 11 — Service boundaries

PHASE C · STEP 11
Assign entity ownership and integration patterns

Decide which service owns which entities. This is where the hardest architectural trade-offs live. Define integration patterns (synchronous API vs event-driven) and consistency boundaries between services.

Inputs
Data model, NFRs, technical services from step 2
Outputs
models/{journey}/service-boundaries.json — aggregated into central-model/service-map.json
Owner
Architect leads — this is a human judgment call with significant downstream consequences. Agent provides options analysis.

Boundary heuristics

  • Entities that are always read and written together belong in the same service
  • Entities that have different consistency requirements may need separate services
  • Entities shared across many journeys are candidates for their own service
  • If two entities have different data classifications, consider separate services for security isolation
  • High revision counts on a boundary (tracked in Jira) signal it should be redrawn

Step 15 — Screen specifications

PHASE D · STEP 15
Specify fields, states, and actions per screen

For each screen, define which data entities and fields are displayed (referencing the data model), which projection rules apply (referencing the participant interaction model), what actions are available (referencing API contracts), and what states the screen can be in.

Inputs
Information architecture, data model, participant interaction model, API contracts
Outputs
ui-specs/{portal}/screens/{screen}.json
Owner
Interaction designer + Agent — designer defines composition and priority, agent fills in field-level detail from the data model

Screen states

Every screen specification must address: loading, empty (no data yet), happy path (normal data), partial data (some API calls succeeded, some failed), error (service unavailable), and forbidden (user lacks entitlement).

Transparency framework

When institutional transparency is a core requirement, it becomes a first-class capability with its own services, data model extensions, and disclosure rules. Every entity gains transparency annotations that control what becomes publicly visible, when, and in what form.

Three layers of transparency

LayerPurposeAudienceLatency
OperationalSystem health, transaction volumesPublic, operators, participantsReal-time
DecisionHow and why decisions were madePublic, researchers, oversightDelayed (30d / 1y)
AccountabilityImmutable record of all actionsOversight, auditors, publicDelayed (1y+)

Design to development handoff

Everything above this section is design, not development. Phases A through D produce specifications — JSON artefacts stored in a repository. They do not produce running software, deployed services, tested UIs, or operational infrastructure. The design pipeline feeds the development pipeline. They are separate concerns staffed by different teams with different workflows.

The relationship between design and development is incremental, not big-bang. As soon as the first journey reaches "stable" in the MODEL project and its screen specs are "approved" in the UXSPEC project, the development team can begin building while the design team continues modelling the next journey.

The handoff contract

A journey is "ready for development" when all of the following are true:

  • All MODEL spec tasks for that journey are in "stable" status
  • The central model has been updated to include the journey's entities
  • All UXSPEC screen specs for screens touched by that journey are "approved"
  • No open "model feedback" issues from UXSPEC are blocking against that journey's entities

The dev team should never build from artefacts that are still in "in progress" or "in review" — the risk of rework is too high. The "stable" and "approved" statuses exist precisely to signal buildability.

Stub-then-replace strategy. Tier 3 analytical services (credit risk, collateral valuation, economic modelling, stress testing, fraud screening) are stubbed in sprints 3–4 and replaced with real implementations when their consuming journeys are built.
