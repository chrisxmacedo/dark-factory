Pipeline Rationale Why this pipeline exists, design decisions, roles, testing strategy, and the reasoning behind each stage

The Core Problem

Why This Pipeline Exists

Software development failures rarely come from a single cause. They come from the accumulation of undetected problems across multiple layers: a function that works in isolation but breaks when integrated, an integration that passes tests but corrupts data silently, a release that passes all automated checks but degrades under real traffic.

Traditional pipelines often conflate these layers — running everything in one CI job, or doing a single round of testing before release. The result is that failures are discovered late, when they are expensive to fix, and the signals that would have caught them early were never designed in.

This pipeline is designed around a different principle: progressive confidence. Each stage is designed to answer one specific question, at the right level of fidelity, with the right kind of evidence.

Progressive Confidence

Each Stage Answers a Different Question

The questions are ordered so that simpler, faster, cheaper checks happen first — and more expensive, slower, system-wide checks happen only when earlier stages have passed.

StageEnvironmentQuestion Answered
In DevelopmentFeature BranchDoes the code work in isolation?
In Local TestFeature BranchDoes the behaviour match the specification?
In Integration TestCIDo components work together?
In E2E Impact TestCIDoes the change work within real system flows?
In Full E2E RegressionRelease CandidateDoes the system still work overall?
Release / ProductionMainIs this version production-ready and live?
Stage Rationale

Early stages are fast and isolated. They give the developer rapid feedback on whether their implementation is correct. Running a full regression suite at the feature branch stage would be slow, noisy, and misleading — many tests would fail for reasons unrelated to the change.

Middle stages introduce real system interaction progressively. Integration tests catch interface and contract failures that unit tests cannot detect. E2E impact tests confirm the change works in real flows without the noise of testing the entire system.

Late stages provide system-wide confidence. The full regression suite only runs against a stable release candidate — not against every feature branch, where it would produce false negatives from in-flight changes by other developers.

Failures are caught by the stage best positioned to diagnose them — not by whatever stage happens to run them first.

Repository States

Branches as Stability Levels

The pipeline is not just a sequence of test runs — it is a sequence of repository states, each representing a different level of stability and integration.

Feature Branch

The developer's working environment. It is explicitly safe to break here — rapid iteration is the goal. The only concern is whether the implementation is correct in isolation and will integrate cleanly.

CI / Integration Branch

The first shared environment. Multiple feature branches merge here. Component interactions are tested for the first time against real dependencies. It is expected to be less stable than the RC, which is why fixes here are acceptable before promoting.

Release Candidate

A snapshot taken from CI. Once cut, it enters a stabilisation phase — no new features, only targeted fixes. Full regression runs here because it represents what would actually be released.

Main

Production-ready or deployed code. The system of record. Nothing reaches Main without passing every preceding gate and receiving explicit human approval. The further right a ticket moves, the higher the confidence — and the higher the cost of a failure discovered at that stage.

Evidence-Based Gating

Evidence Types

Each stage gate requires concrete evidence, not a teammate's claim or a pipeline passing without inspection.

Evidence TypeWhat It Verifies
Test resultsPass/fail counts, specific failure messages, coverage delta. Not just "tests passed" — which tests, how many, what changed.
Data validationWhere state is mutated, the database state, event payloads, and data structures are correct. Surface-level responses can pass while data is silently corrupted.
ObservabilityStructured logs, correlation IDs, traces, and metrics are confirmed present. Validates correct behaviour and ensures the system remains observable in production.
A pipeline that passes without evidence is not a pipeline — it is an optimism machine. Gates must be based on verifiable artefacts.

Human Gates

Why Exactly Two

The pipeline has exactly two points where a human must take explicit action. Every other transition is automated — because every other transition is based on objective, verifiable evidence that an agent team can assess.

GateAction RequiredWhy Human Judgement Is Needed
Ready for DevHuman moves ticket in JiraRefinement requires product and engineering judgement — priority, scope clarity, dependency awareness — that no agent can assess.
Promote to MainHuman replies "Approve promote {KEY}-xxx"Deploying to production is a business decision. Even with all tests passing, timing, risk tolerance, and business context require human decision-making.

Adding more human gates would slow the pipeline without adding safety. Removing these two would eliminate the human judgement that cannot be automated.

Agent Team Design

Agent Primitives

Claude Code's agent team feature allows a session to spawn multiple sub-agents that collaborate through two shared primitives:

Shared Task List

A JSON file maintained locally that agents can read, claim tasks from, and mark complete. Tasks can have dependencies and blockers, so later tasks do not start until earlier ones resolve. Lives only for the duration of a session.

Inbox System

Each agent has a message inbox. Agents can send findings, critiques, and status updates to each other and to the team lead in real time during a session. Enables genuine parallel collaboration — agents work simultaneously while staying coordinated.

Both primitives are local to the Claude Code session. They are not Jira — Jira is the persistent system of record.
Spawning Patterns

Claude Code supports three distinct ways to use sub-agents. This pipeline uses Pattern 2.

PatternDescriptionUsed For
1 — One-shotSingle agent does a focused task and returns the result. No shared state.Simple delegation, short-lived tasks
2 — Persistent teamTeam lead spawns multiple teammates from a shared task list. Teammates persist, message each other, report back. Team lead is long-lived.This pipeline — all six stages
3 — Sequential agentsSingle agents handle one status each, work independently, shut down when done.Simple single-agent workflows
Why Pattern 2

Each stage has a different skill and risk profile

Implementation requires creativity, exploration, and iteration. Testing requires rigour and scepticism. Deployment requires caution above everything else. These capabilities are better served by teams configured differently rather than a monolithic team that tries to change its character mid-session.

Jira is the reliable handoff mechanism

By having each team read from Jira cold — fetching the ticket, the PR, and comments from the previous team — the system avoids depending on in-memory state from a previous session. Each team must ground itself in the artefacts. This forces explicit documentation of decisions at each stage via Jira comments, making the pipeline state auditable across sessions.

Parallel agents provide real-time quality control

Within each team, specialist agents work in parallel. In the Development Team, the Devil's Advocate reviews commits as they are made — not after implementation is complete. In the Integration Team, the Observability Checker runs in parallel with the CI Monitor. The inbox system allows a team to converge on a result from multiple angles simultaneously.

Teams are long-lived within a session

The Team Lead does not shut down between tickets. Move tickets to Ready for Dev in Jira, and the Team Lead picks them up and works them through progressively. Message the Team Lead at any point for a status report, to skip a ticket, or to adjust priority.

Internal Tasks vs Jira

This is the most important architectural distinction to understand.

// Jira — persistent, cross-session system of record
PRJ-42: In Development
    |
// Team Lead reads ticket, creates short-lived internal task list
[Task A] Explore codebase     -> claimed by Implementer
[Task B] Review implementation -> claimed by Devil's Advocate
    |
// When complete, Team Lead writes the permanent record
PRJ-42: Ready for Local Test
Comment: "Development complete. Branch: feature/PRJ-42/..."

The internal task list lives only for the duration of the team's work on that ticket. The Jira transition and comment are the permanent record. This design is resilient to session interruptions — if a session ends mid-ticket, the ticket remains in its "In..." status in Jira and the next session's Team Lead can restart from that stage.

Jira is the system of record. The internal task list is a coordination scratch-pad. Never confuse the two.

Roles & Responsibilities

The Two-Role Model

The pipeline separates work into two distinct professional roles. This separation reflects a genuine difference in perspective, objective, and skill — not just a naming convention.

The two roles exist because the question "did we build it correctly?" (engineer) is fundamentally different from "does it behave correctly?" (test developer). Conflating them produces blind spots.
Software Engineer

Primary concern: Is the implementation correct? Operates on the feature branch.

  • Understands the acceptance criteria and translates them into code
  • Explores the existing codebase before writing anything new
  • Makes implementation decisions coherent with existing patterns in CLAUDE.md
  • Writes code that is correct, maintainable, and testable
  • Writes unit tests and component tests as part of implementation — not as a separate activity

Why engineers write unit and component tests

Unit and component tests are the engineer's primary mechanism for verifying their implementation is correct. They are written alongside the code because they are the fastest feedback loop (milliseconds, not minutes), they force thinking about testability during implementation, and they document expected behaviour at the level of detail only the engineer has while writing the code.

These tests are not the Test Developer's responsibility because they require intimate knowledge of implementation internals. The Test Developer verifies behaviour from the outside — they cannot write a meaningful unit test for code they did not write.

Test Developer

Primary concern: Does the system behave correctly? Operates across Local Test, Integration, E2E, and Regression stages.

  • Defines test scenarios covering acceptance criteria from a behavioural perspective
  • Designs tests that validate system-level interactions: integration, E2E flows, cross-service consistency
  • Ensures data is validated at the right points — not just surface responses, but underlying state
  • Ensures the system is observable: failures produce useful signals, correct behaviour is confirmed through those signals

Why test developers are separate from engineers

The Test Developer brings a different kind of scepticism. Where the engineer is optimistic about their implementation (they wrote it to work), the Test Developer's role is to find the ways it does not. Additionally, the Test Developer is responsible for system-level validation the engineer is not positioned to perform: testing the feature against the real system, validating whether it does what the acceptance criteria requires, and validating the contracts between components.

Key Agent Roles

The Devil's Advocate

The Devil's Advocate runs in parallel with the Implementer during development, reviewing each commit as it is made and sending critiques via inbox. This is one of the most important agents in the pipeline.

Real-time critique over post-implementation review

When a critique arrives while the engineer is still implementing, it can be addressed in the next commit. When it arrives after implementation is complete, addressing it requires unpicking decisions that may have cascading effects. The earlier a problem is surfaced, the cheaper it is to fix.

Complementary information

The Implementer knows the implementation in detail. The Devil's Advocate knows the acceptance criteria and the existing codebase patterns. Running in parallel and communicating through the inbox combines both perspectives in real time — something impossible in a serial review model.

Advisory by default, blocking only on high severity

Low and medium findings are recorded but do not stop the Implementer. High-severity findings — security issues, data integrity risks, clear acceptance criteria violations — require acknowledgement before the completion gate passes. This design adds quality without becoming a bottleneck.

The Team Lead

The Team Lead does not write code, run tests, or deploy. Its role is coordination and gate-keeping. It is the single agent that reads from and writes to Jira.

Why a dedicated Team Lead rather than self-coordinating agents?

Self-coordination between agents is fragile. If the Implementer signals the Test Writer directly, the logic for what happens next is distributed across multiple agents — any of them could miss a message, misinterpret a state, or make a transition prematurely.

The Team Lead centralises these decisions. It reads the Jira ticket and passes full context to every agent it spawns. It receives structured inbox messages from all agents. It verifies completion gates before any Jira transition. This means Jira state is always consistent with what the Team Lead has explicitly verified — not with what any individual agent claims.

One agent writes to Jira. One agent makes transition decisions. This is the invariant that keeps the pipeline state reliable and auditable.

Testing Strategy

Test Layers

Testing in this pipeline is a series of distinct validation layers. The layers build on each other — tests written at an earlier stage continue to run at later stages. Each stage adds a new layer on top of the existing ones.

StageOwnerTest TypeQuestion
In DevelopmentSoftware EngineerUnit testsDoes this function/class do what it is supposed to do?
In DevelopmentSoftware EngineerComponent testsDoes this module/service boundary behave correctly?
In Local TestTest DeveloperLocal integration testsDo components within this feature interact correctly?
In Local TestTest DeveloperBehaviour testsDoes the implementation satisfy the acceptance criteria?
In Integration TestTest DeveloperIntegration tests (real)Do components work together in the shared environment?
In Integration TestTest DeveloperContract testsAre the interfaces between services compatible?
In E2E Impact TestTest DeveloperE2E impact testsDoes this change work within the real system flows it affects?
In Full E2E RegressionTest DeveloperFull E2E regressionDoes the entire system still work?
Data Validation Strategy

Surface-level test assertions are not sufficient for critical flows. A test can pass — the API returns 200, the UI shows the right data — while the underlying data is silently incorrect.

StageData Validation Requirements
Local TestVerify database row created/updated/deleted. Verify returned data structure matches expected schema. Confirm nothing silently dropped.
Integration TestTrace data mutations across service boundaries using correlation IDs. Verify events published by one service are received and processed correctly by consumers.
E2E Impact TestVerify end-to-end data integrity — data enters, transforms correctly at each stage, exits in expected state. Trace through every service hop.
RegressionRe-verify all above against RC. Confirm migrations applied correctly and have not corrupted existing data.
E2E tests that pass with incorrect data are worse than tests that fail. They create false confidence. Every state-mutating flow requires data-level assertions.
Observability Requirements

Observability is a validation requirement at every stage from CI onwards. A change that cannot be observed cannot be validated in production.

SignalRequirementWhy
Structured loggingJSON logs at key decision points: request received (with correlation ID), key logic decisions, errors with full context, request completed with outcome.Enables automated assertion — verify correct log lines emitted, not just that the API returned 200.
Correlation IDsEvery request crossing a service boundary must carry a correlation ID. Required from integration stage onwards.Enables end-to-end tracing across multiple services in a single query.
Metrics & tracesRequest latency histograms (p50/p95/p99), error rate counters, distributed traces for multi-service flows.Monitored by the Production Observer in the 15-minute post-deploy stabilisation window.
Gate: Observability is a gate at the integration stage — not a post-release concern. If the change cannot be observed in the integration environment, it will not pass this stage.

Stalled Tickets

A ticket in an "In..." status with no active agent team is stalled. This can happen if a session ends mid-work, or if a team shuts down without transitioning properly.

Detecting stalled tickets

project = {PROJECT_KEY} AND status in (
  "In Development",
  "In Local Test",
  "In Integration Test",
  "In E2E Impact Test",
  "In Full E2E Regression"
) AND updated < -2h

Recovery

Transition the ticket back to the previous "Ready for..." status manually in Jira. On the next Claude Code session, the Team Lead will pick it up and restart the relevant team from that stage. No state is lost — all previous work is preserved in the branch, PR, and Jira comments.

Why This Pipeline for Solo & Small Teams

Disproportionate Risk

The progressive confidence model is sometimes associated with large engineering organisations. For a solo developer or small team, the rationale is different but equally strong.

The cost of a production incident is disproportionately high. There is no on-call rotation, no dedicated QA, no second pair of eyes. The pipeline compensates for the absence of those human checks by encoding them as automated gates at every stage.

The agent team system means the overhead of running this pipeline is low. Teams are spawned automatically, work in parallel, and report structured results. The developer interacts with the pipeline at the two human gates and is otherwise free to work on the next ticket while the current one progresses through the stages.
