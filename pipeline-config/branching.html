Branching Model Four branch types, merge rules, and the permanent audit trail

Branch Structure

Overview

  |
  └──> ci    ← receives only: feature branch merges (after local tests pass)
                              RC back-merge (immediately after RC → main)
        |
        |──> feature/{PROJECT_KEY}-{key}/{slug}

        |     Implementer opens PR as signal — Team Lead merges
        |     Branch NEVER deleted after merge
        |

              Fix Agent may commit bug fixes for genuine regressions

Branch Types

main

Production branch. Receives only merges from release branches. No direct commits ever. Tagged with semver after each release merge.

ci

Integration branch. Receives feature branch merges (after local tests pass) and back-merges from main (after RC promotion). The first point where changes interact with each other.

feature/{PROJECT_KEY}-{key}/{slug}

Created by Team Lead when a Deliverable enters In Development. Development and Local Test teams commit here. The Implementer opens a PR targeting ci as a signal — the Team Lead merges it. Never deleted after merge.

release-rc-{n}

Cut from HEAD of ci by the Team Lead after E2E impact tests pass. Each release branch is single-use and independent. The Regression team validates here; Fix Agent may commit bug fixes for genuine regressions. Merged to main after human approval, then back-merged to ci. Never deleted.

Who Does What

Branch Responsibilities

The Team Lead is the only agent that creates branches or performs merges. Specialist teams commit only to their designated branch.

ActionWhenCommand
Create feature branch Ticket enters In Development git checkout -b feature/{KEY}-{n}/{slug} ci
Merge feature to ci Local tests pass Rebase feature onto ci, then git merge --no-ff
Cut release branch E2E impact tests pass git checkout -b release-rc-{n} ci
Merge RC to main Human approves git checkout main && git merge --no-ff release-rc-{n}
Tag main After RC merge git tag v{x}.{y}.0 -m "..."
Back-merge to ci After tagging git checkout ci && git merge --no-ff main

Rebase Rules

When to Rebase vs When Not To
MergeRebase?Why
Feature → ciYesLinearises dev work before integration
RC → mainNoPreserves the integration point
main → ci (back-merge)Noci absorbs main's state
Critical: Never rebase ci, release, or main branches. Rebasing shared branches flattens merge topology and loses the audit trail of where integrations happened.

Merge Strategy

Rules
  • All merges use --no-ff to create explicit merge commits
  • Never squash — preserves full commit history
  • Never fast-forward — integration points must be visible in the graph
  • Never delete any branch — permanent audit trail
  • Never commit directly to main — main only receives merges from release branches

Branch Deletion Policy

Permanent Audit Trail

No branch is ever deleted. Feature branches, release branches, and all others are retained permanently after their merges complete. This provides a full audit trail of every change, every release candidate, and every merge point.

Versioning

Tagging

Immediately after merging an RC into main, tag the merge commit with a semver tag (e.g. v0.1.0) and push the tag. Back-merge happens after tagging. Increment the minor version per Deliverable.
