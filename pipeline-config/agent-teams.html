Agent Teams Seven specialist teams, their roles, signals, and completion gates

1. Refinement Team

Overview
TriggerTicket status: In Refinement (auto-picked from Backlog)
BranchNone — pre-code analysis only
Confidence Goal"The implementation approach is sound and the tasks are concrete"
Shuts Down WhenTicket transitions to In Development
Team Composition

Solution Designer

  • Reads the full Deliverable: business rules, Gherkin AC, data model, API surface, dependencies
  • Reads ARCHITECTURE.md for target architecture
  • Reads REPO_MAP.md for each affected repo (current structure, modules, patterns)
  • Proposes implementation approach: which repos, files to modify/create, patterns to follow, data flow, integration points
  • Sends SOLUTION DESIGN to Team Lead

Task Planner

  • Receives the Solution Design
  • Breaks approach into concrete Jira Tasks under the Deliverable
  • Each Task includes: specific file paths, pattern to follow, acceptance criteria, dependencies, complexity (S/M/L)
  • Tasks ordered by dependency — Development Team works through them in sequence
  • Creates Tasks via jiractl create Task
  • Sends TASKS CREATED to Team Lead

Risk Assessor

  • Runs in parallel with Task Planner
  • Checks for: architectural violations, existing code conflicts, missing dependencies, schema migration risks, security concerns, test coverage gaps
  • Sends RISK ASSESSMENT to Team Lead
Completion Gate
  • Solution Design received and reviewed
  • All Tasks created in Jira with file paths, patterns, and acceptance criteria
  • Tasks ordered by dependency
  • Risk Assessment received with no blocking concerns
  • Deliverable description updated with "Solution Design" section

If insufficient detail in the Deliverable → return to Backlog with comment listing what's missing.

If blocking risks found → add needs-human label, do not proceed.

2. Development Team

Overview
TriggerTicket status: In Development
Branchfeature/{PROJECT_KEY}-{key}/{slug}
Confidence Goal"This change works in isolation"
Shuts Down WhenTicket transitions to In Local Test
Team Composition

Implementer (Software Engineer)

  • Reads full ticket, explores codebase before writing code
  • Commits after every file change — never batches unrelated changes
  • Every commit pushed immediately to origin
  • Every commit message includes the Deliverable Jira ID
  • Writes unit tests, component tests, and startup smoke test
  • Opens PR targeting ci on completion (does not merge)
  • Adds Jira comment summarising what was built and tested
  • Transitions child Task tickets (In Progress / Done) as work proceeds

Devil's Advocate (Quality Oversight)

  • Runs alongside the Implementer — never commits
  • Reviews each commit against acceptance criteria, patterns, edge cases, security, testability
  • Sends critiques: CRITIQUE [low|medium|high]: [issue] — [suggestion]
  • Sends FINAL REVIEW when development signals complete

Test Writer (Test Developer)

  • Runs alongside the Implementer — writes tests as implementation progresses
  • Writes behaviour tests (one per acceptance criterion minimum), edge case tests, local integration tests
  • All tests include data-level assertions for state-mutating flows
  • Signals: TESTS WRITTEN. [N] tests ([breakdown]). All passing.
Completion Gate

Team Lead verifies after receiving all three signals (DEVELOPMENT COMPLETE, TESTS WRITTEN, FINAL REVIEW):

  • Feature branch exists and pushed
  • PR open targeting ci with ticket key
  • All test layers passing: unit, component, behaviour, edge case, integration
  • Lint and format checks pass (ruff check, ruff format --check)
  • Data-level assertions present for state-mutating flows
  • All high-severity critiques addressed
  • No uncommitted changes

3. Local Test Team

Overview
TriggerTicket status: In Local Test
Branchfeature/{PROJECT_KEY}-{key}/{slug} (same as dev)
Confidence Goal"This change works in isolation"
Shuts Down WhenTeam Lead merges PR to ci
Team Composition

Test Runner

  • Startup smoke test first — app must boot from clean state
  • Page render check (web projects) — all pages render with expected data
  • Runs full local test suite (unit + component + integration + behaviour)
  • Never commits — reports results only

Fix Agent (conditional)

  • Only spawned if Test Runner reports failures
  • Commits fixes to feature branch only
  • Maximum 2 fix attempts, then escalates
Completion Gate
  • All test layers pass with zero failures
  • Data-level assertions present
  • No uncommitted changes
  • Coverage delta acceptable

Team adds Jira comment summarising results. Team Lead then rebases feature onto ci, merges with --no-ff, and transitions to In Integration Test.

4. Integration Test Team

Overview
TriggerTicket status: In Integration Test
Branchci
Confidence Goal"This change works with other components"
Team Composition (3 members in parallel)

CI Monitor

Watches CI pipeline, verifies pytest + ruff check + ruff format all pass.

Integration Analyst

Contract validation, downstream impact, data consistency, migration safety, recent merge conflicts.

Observability Checker

Structured logs, correlation IDs, new signals confirmed present.

Fix Agent (conditional)

Commits to ci only if CI gates fail. Max 2 fix attempts.

Completion Gate
  • CI pipeline fully green
  • Contract validation passed
  • Downstream impact assessed
  • Data consistency confirmed
  • Observability signals confirmed

Team adds Jira comment. Transitions to Ready for E2E Impact Test.

5. E2E Impact Team

Overview
TriggerTicket status: In E2E Impact Test
Branchci
Confidence Goal"This change works within real system flows"
Team Composition

Impact Analyst

Produces structured impact map: affected user journeys, system flows, data paths, observability hooks.

E2E Runner

Executes E2E tests for affected journeys only. Validates API responses, database state, event processing, correlation ID tracing.

Fix Agent (conditional)

Only for genuine regressions. Max 2 fix attempts.

Completion Gate
  • All affected journeys pass E2E
  • Data-level assertions confirmed
  • Observability signals confirmed
  • ci branch clean and stable

Team adds Jira comment. Team Lead cuts release-rc-{n} from ci and transitions to In Full E2E Regression.

6. Regression Team

Overview
TriggerTicket status: In Full E2E Regression
Branchrelease-rc-{n}
Confidence Goal"The system is stable and ready for release"
Team Composition

Regression Runner

Executes the full E2E regression suite — every test, every journey, cross-system validation.

Regression Analyst

Assesses release readiness: environment parity, migration sequencing, feature flags, third-party integrations, observability, rollback plan.

Flake Investigator (conditional)

Re-runs failures to distinguish flaky from genuine. Max 2 re-run cycles.

Fix Agent (conditional)

Commits bug fixes to release-rc-{n} for confirmed regressions. Max 2 fix attempts.

Human Approval Gate

This team does NOT automatically promote. The Team Lead requests human approval and waits for explicit confirmation before proceeding.

7. Release Team

Overview
TriggerExplicit human approval
BranchTeam Lead merges release-rc-{n} → main, back-merges → ci
Confidence Goal"This version is production-ready and live"
Team Composition

Release Manager

Confirms RC branch integrity and pre-release steps. Does not merge — signals Team Lead.

Deploy Agent

Triggers production deployment. On failure: STOP, do not rollback, report immediately.

Production Smoke Tester

Health endpoints, critical journeys, third-party integrations. On failure: STOP, report.

Production Observer (15 minutes)

Monitors error rates, latency, log patterns for 15-minute stabilisation window.

Hard Rules
  • Never merge to main without explicit human approval
  • Never delete any branch
  • Never rebase or squash — always merge commits
  • Never rollback without human instruction
  • Never re-trigger a failed pipeline without human instruction

Common Rules Across All Teams

Universal Commit Rules
  • Commit after every file change — never batch unrelated changes
  • Every commit pushed immediately to origin
  • Every commit message includes the Deliverable Jira ID
  • Each team adds a Jira comment on the ticket summarising their work on completion
  • Each team includes a RETROSPECTIVE in their completion signal
