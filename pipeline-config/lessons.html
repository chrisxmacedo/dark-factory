Lessons Learned 24 improvements discovered during real-world pipeline usage

These improvements were discovered during the first real-world usage of the pipeline. All have been applied to the starter templates. They are documented here so that new implementations can avoid the same issues.

Repository & Git

Separate repos per service

Do not use a monorepo. Each service must be its own standalone git repo. Tools and IDEs cannot find .git when the service is a subdirectory of a larger repo.

GitHub org correction

Agents may push to a personal account instead of the organisation. The development team agent file must specify the correct GitHub org explicitly. All repos must be created under the project org.

Repo scope

Only code directories should be tracked in git. Documentation, config (.claude/), and local reference files stay local and untracked via .gitignore.

Rebase only feature branches

Rebasing a release branch onto main flattens merge commits and loses integration topology. Only feature branches should be rebased (onto ci). RC → main and back-merge → ci use --no-ff only, no rebase.

No direct commits on main

A direct commit to main caused a merge conflict when the RC was promoted. Main only receives merges from release branches. Even hotfixes must follow the branch flow.

Commit Discipline

One commit per file change

Agents were batching 11 files into one commit. Each file change should be its own commit with an explanation of what changed and why.

Jira ID in all commits

Commits without ticket IDs break traceability. Every commit must be prefixed with the Deliverable Jira ID (e.g. PRJ-208: T3: Implement parser).

Push after every commit

Local-only commits risk being lost if the session is interrupted. Every git commit must be immediately followed by git push origin <branch>.

Tag main on every release

Every RC → main merge gets a semver tag. Increment minor version per Deliverable. Tags are pushed immediately.

Jira Configuration

Create statuses before referencing them

The pipeline referenced 9 statuses that didn't exist in Jira. All statuses must be created and transition IDs retrieved before the pipeline can operate.

Status name mismatch

Jira may use "Selected for Development" instead of "Ready for Dev". The polling queries must match the exact Jira status names. Consider adding a status-name mapping table to CLAUDE.md.

Jira transitions must not be batched

A Jira transition batched with a rejectable Bash command caused the transition to be silently discarded when the user rejected the Bash call. Jira state changes must be sent as their own message, confirmed before proceeding.

Task vs Deliverable separation

Tasks use a simple 3-status workflow (Backlog → In Progress → Done). Only Deliverables flow through the full pipeline. The dev team owns Task transitions, not the Team Lead.

Testing

Startup smoke test required

All 249 tests passed but the app returned 500 on every endpoint. Root cause: tables weren't created on startup — test fixtures masked the issue. Always verify the app boots from a clean state (empty DB, default config) without errors.

Lint and format gates

The development team must run ruff check and ruff format --check before signalling completion. Without this, the integration team discovers lint failures that should have been caught earlier.

Bug analysis must trace the full path

Three bugs were diagnosed one at a time because investigation stopped at the first plausible cause. Always trace the full request path: browser → frontend → API → service → external dependency. Check CORS, headers, request/response bodies at each hop.

Pipeline Operations

CLAUDE.md changes go direct to ci/main

Pipeline configuration changes are infrastructure, not features. Commit directly to ci and merge to main — do not route through feature branches.

One ticket at a time

Concurrent tickets increase merge conflict risk, make state tracking harder, and reduce focus. Complete the full pipeline before polling for the next ticket.

Team retrospectives after every stage

Every team reports workflow issues and improvement suggestions at completion. The pipeline is self-improving — issues discovered by one team inform the next deliverable's run.

Platform file for external services

External service details were scattered across config files and env vars. A central platform.md documenting all services, their purpose, and env vars prevents this.

Key Insight

The Pipeline Self-Improves

Every team reports a retrospective at completion. The Team Lead logs all retrospectives and applies concrete improvements to both the project agents and the starter templates. Over 24 improvements were discovered and applied during the first day of real usage. The improvements flow both ways — project-specific fixes are applied back to the templates so future projects benefit.
